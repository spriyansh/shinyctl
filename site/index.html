Shiny apps that stay up.

shinyctl runs each R Shiny app as several copies behind a built-in load balancer, with a warm spare ready to take over, and redeploys without cutting anyone off. One binary. No Docker, no root.

$ curl -fsSL https://raw.githubusercontent.com/spriyansh/shinyctl/main/install.sh | sh

Or with Go 1.26.10: go install github.com/spriyansh/shinyctl@v0.1.0. Other ways are on the install page.

What you just watched

The same session, said plainly. The numbers come from the release test on a Raspberry Pi 5, with requests running the whole time.

One port, several copies

Each app runs as replicas active copies plus warm-replicas spares, all behind the one port in your manifest. A cookie keeps each visitor on the same copy, so Shiny sessions work.

default: 1 active copy, 1 warm spare · cookie lb_<port>

A copy dies, the page keeps answering

The load balancer sends the next request to the warm spare at once. shinyctl restarts the dead copy, with a backoff, and it becomes the new spare.

spare took over in 0.04 s · 0 of 414 requests failed

Redeploys that drain

restart, or an apply that changes how the app starts, brings up new copies first. Old copies keep their visitors until those leave or drain-timeout passes. A new version that fails to start never takes over.

drain-timeout 15m by default · --now skips the wait

Upgrades and reboots

A new shinyctl starts its load balancer next to the old one and takes over without refusing a connection. On Linux, shinyctl startup adds a systemd user unit, so apps come back after a reboot.

two upgrades under load · 0 of 473 and 0 of 470 failed

How it works

One binary runs as three things: the shinyctl command you type, shinyctl-api in the background, and the load balancer in front of your apps. If shinyctl-api stops, the load balancer and the copies keep serving, and a new one adopts them. More on how it works.
